# Groq: этап 10 — живая приёмка и общие квоты

Дата: 2026-10-21. SDK `groq==0.37.1`, модель `openai/gpt-oss-120b`.
Ключ предоставлен пользователем для реальной приёмки, вводился через скрытый prompt
и использовался только в памяти процесса. `.env` не менялся. Telegram polling,
уведомления пользователям и production rollout не запускались.

## Методика и воспроизводимость

Публичный Terricon API `https://server.terricon.kz/terra/api/getAllEvents` проверен
по шести комбинациям lang/theme: RU и KZ по 133 IT + 54 business + 21 marketing = 208 событий,
invalid 0, каждая выборка принята с первой попытки. Полный нормализованный snapshot
временный; его SHA256 сохранён в fixture. В репозитории оставлены только 24 выбранных
события с исходными title/description/audience/speaker обеих официальных локалей:
[`stage10-real-events.json`](../../tests/fixtures/groq/stage10-real-events.json).

Разметка заморожена **до inference**, автор — implementing agent. Это не независимая
человеческая gold-выборка и не оценка обобщения на невидимых данных. По 8 случаев
используют только RU, только KZ, обе локали. Тематические обязательные категории и
допустимые дополнительные категории фиксируются отдельно; passed означает все
обязательные присутствуют, лишних за пределами допустимых нет. Среди случаев есть
смешанные IT/finance, AI/products, AI/design и `other` для общей климатической лекции.

Первый полный classification baseline сохранён отдельно:
[`v2 results`](groq-stage10-2026-10-21-results.json). Результат 18/24; 4 семантических
расхождения и2 HTTP 400, причины400 исходный runner не записывал. После 24 классификаций
и 3 переводов baseline остановлен, чтобы не расходовать квоту на оставшиеся проверки
старой версии. Невыполненные baseline translation/edge cases не считаются пройденными.

Prompt v3 определяет смысл каждой категории, отделяет тему от аудитории и явно
обрабатывает `other` и AI/design. Метки после получения ответов не менялись.
Повторная выборка — регрессия по уже известным случаям, а не отдельный holdout.
Итоговый evidence: [`v3 results`](groq-stage10-2026-10-21-v3-results.json).
В нём сохраняются dataset SHA, fingerprint prompt/schema/output settings, ответы,
input/output/reasoning tokens, latency и только разрешённые rate-limit headers.
HTTP ошибки имеют безопасный код; тексты ошибок провайдера/секреты не сохраняются.

Runner валидирует fixture до запросов и требует отдельную мигрированную БД:

```bash
uv run python -m terricon_events_bot.infrastructure.groq_acceptance \
  --output /tmp/groq-acceptance.json --dry-run

# GROQ_ACCEPTANCE_DATABASE_URL указывает на ОДНОРАЗОВУЮ БД, уже upgrade head.
# Если GROQ_API_KEY отсутствует в окружении, runner запросит его скрыто.
uv run python -m terricon_events_bot.infrastructure.groq_acceptance \
  --output /tmp/groq-acceptance.json
```

`--resume` допускается только с тем же dataset/model/behavior fingerprint. Новый
prompt или allowance требуют нового отчёта. Fixtures не входят в runtime image;
для runner из image нужен отдельный путь `--input`. Production DATABASE_URL для
приёмочного runner не использовать. Он не запускает importer, polling или delivery.

## Квоты и ограничения

Account headers подтвердили RPD 1000 и TPM 8000. Пользователь отдельно сверил на
странице Limits RPM 30 и TPD 200000. Отдельные ITPM/OTPM не заявлены; если они появятся
у аккаунта, текущих четырёх настроек недостаточно для их отдельного ограничения.
Источник правил и семантики заголовков:
[официальная документация Groq](https://console.groq.com/docs/rate-limits).

`GROQ_RPM=24`, `GROQ_RPD=800`, `GROQ_TPM=6400`, `GROQ_TPD=160000` оставляют 20% от
подтверждённого account capacity. Классификация и перевод используют один
`GROQ_QUOTA_SCOPE=groq:default` и общую PostgreSQL БД. Для других ключей той же
организации, использующих тот же сервис/БД, scope должен совпадать; менять его
при рестарте или ротации ключа нельзя, иначе исчезнет связь с прежними резервами.

Миграция 0011 добавляет `ai_quota_states` и `ai_quota_reservations`. Резерв создаётся
атомарно под блокировкой строки scope **до HTTP**, транзакция завершается до сети.
Скользящие окна60 с / 24 ч переживают рестарт; дневной интервал намеренно консервативнее
календарного reset. До запроса считаются UTF-8 байты payload/schema/instructions,
512 токенов служебного запаса и весь output allowance; после ответа резерв заменяется
actual input+output. Reasoning — часть output, повторно в квоты не прибавляется.
Если usage неизвестен или процесс упал, полный резерв остаётся до истечения окна.
Это оценка с запасом для GPT-OSS, а не универсальный точный tokenizer всех моделей.

Остатки из headers могут только уменьшать локальную доступность до reset; из них
вычитаются другие незавершённые резервы. Устаревший параллельный ответ не пополняет
квоту. HTTP 429/Retry-After сохраняет общий cooldown и блокирует обе операции даже
после рестарта. Больше TPM/TPD на один запрос — безопасный `quota_request_too_large`,
без HTTP; классификация затем проходит обычный retry/fallback. Истёкший24 h fallback
имеет приоритет перед новым запросом, который мог бы остановить batch по квоте.

Другие приложения организации без общей БД могут израсходовать квоту после любого
полученного header. Предсказать их будущий расход нельзя; оставлен запас и реакция
на реальные headers/429. Исчерпание полного account quota намеренно не провоцировалось:
отказы/восстановление проверялись MockTransport и настоящей PostgreSQL, live подтвердил
headers и локальные отсрочки. Достаточность Free для произвольной повторной загрузки
или чужого неограниченного расхода не заявляется.

HTTP 400 в v3 имел безопасный provider code `json_validate_failed`.
Это отказ генерации у Groq; успешный ответ модели с неверными категориями не выдавался.
Адаптер теперь нормализует такой код в `invalid_output`, очередь повторяет его обычным
порядком; body/failed_generation не попадают в логи. Свежий recovery —
[`отдельный evidence`](groq-stage10-2026-10-21-recovery-results.json), первоначальный
отказ не удалён и не считается успешным с первой попытки. Настоящий HTTP 429 не возникал.

Latency включает работу adapter/DB/HTTP, но не ожидание квоты во внешнем цикле runner.
Во всех текущих прогонах 67 HTTP-запросов: 64 с известным usage, 3 provider HTTP 400без usage.
Известный расход: **30 557 input + 7392 output = 37 949 токенов**, reasoning 4254 уже включены
в output. Стоимость в локальном Free pricing 0; это не утверждение о платном тарифе.

Максимальный classification output 109 токенов, translation 757; allowance уменьшен
с 2048/4096 до **512/2048**, сохраняя запас для reasoning. При этом длинный реальный
translation real-9698больше не отклоняется локальной предварительной оценкой.
Для других моделей/существенно более длинных текстов нужна новая калибровка;
огромные запросы по-прежнему безопасно отклоняются до сети.

При среднем 674,4 токена / реальную classification разовый импорт 208 событий оценивается
примерно в 140 300 токенов и 208 запросов — внутри выделенного TPD 160 000 / RPD 800.
Все 208 имеют обе официальные локали, поэтому перевод в таком импорте не требуется.
Это прогноз по выборке, а не фактический AI-прогон всех 208. При отсутствии локали
у всех 208ещё примерно 139 300 токенов перевода дадут около 279 600 за 24 ч, выше выбранного
TPD и полного Free 200 000; часть задач будет ждать/получит штатный24 h fallback.
Регулярные sync не должны переклассифицировать неизменившиеся semantic hashes.
Неограниченные повторные импорты и неизвестный расход других приложений Free не покрывает.

## Языковая граница приёмки

Живая проверка заметила изменение поля speaker `Мустафина`→`Мұстафина`. Адаптер v4
теперь всегда копирует speaker из источника и не позволяет заполнить исходные
null description/audience/speaker. RED→GREEN и две реальные проверки сохранены в
[`translation v4 evidence`](groq-stage10-2026-10-21-translation-v4-results.json).
Генерация текста не менялась, постобработка защищает эти структурированные поля.

Смысл переводов проверен агентом: основные факты, термины, URL, paragraph breaks
сохранены. Независимая проверка носителем KZ **не выполнена**. В частности, внутри
свободного description real-9698 RU→KZ встречается `Серикова`→`Серікова`; точное
написание произвольных имён внутри текста программно не гарантируется полем speaker.
Этот вопрос и естественность KZ остаются открытой языковой частью этапа 10. Новая
эвристика распознавания имён без структурированных данных не добавлялась: она могла
бы ошибочно запретить перевод обычных слов. Метки gold после inference не менялись.

Техническая реализация и инструментальная приёмка этапа 10 завершены, языковой gate
остаётся открытым. 20B не сравнивался: после уточнения prompt все 24 реальных случая
классифицированы по разметке; единичный provider JSON failure обрабатывается retry.
Public KZ UI gate исходной спецификации также остаётся отдельным требованием.

Финальный код: **266 tests PASS**, Ruff/format 123 файла, mypy 56 source files,
lock/build/shell/diff PASS. Docker пересобран после speaker/error fixes, preflight
финального образа повторён. Restore 0011 / 27 tables прошёл до этих двух Python-правок;
SQL после restore не менялся. На момент приёмки commit/push/deploy не выполнялись.
Последующая разрешённая публикация отражается в `docs/handoffs/current.md`.

Одноразовый PostgreSQL контейнер и его volume, временный dump и полный source snapshot
после проверок удалены. Проверочный образ оставлен; рабочие сервисы не менялись.
