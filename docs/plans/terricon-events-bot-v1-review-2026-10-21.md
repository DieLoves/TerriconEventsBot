# Независимое ревью Terricon Events Bot v1 (после этапа 10)

Статус: завершён 2026-10-21 (локально, без commit/push и production rollout).

Цель — повторно проверить реализованный проект на дефекты, уязвимости и слабые места
UX/производительности, сверив код с реальными данными публичного Terricon API
(read-only, 6/6 endpoint, 208 событий). Архитектура (domain/application/infrastructure,
очереди в PostgreSQL, один процесс aiogram + APScheduler) признана адекватной;
переписывать её не требуется.

## Найдено и исправлено

Каждый пункт закрыт regression-тестом (RED → GREEN).

1. **Спам уведомлений о прошедших событиях.** В живом API событие после проведения
   получает статус `end_mitap` и ссылку на запись вместо регистрации, поэтому
   `registration_url` меняется → `IMPORTANT_CHANGE` каждому подписчику; исчезновение
   старого события из архива давало `CANCELLATION`. `OutboxService.materialize` теперь
   не создаёт доставки для событий, чей день проведения (Asia/Almaty) уже прошёл —
   то же правило, что у каталога. Domain changes сохраняются для аудита.
2. **Команды админа перехватывались ожиданием ответа/рассылки.** При открытом ответе на
   тикет `/start` и другие команды отправлялись пользователю как ответ, а при черновике
   рассылки становились её текстом. Команды теперь пропускаются; добавлена `/cancel`
   (сбрасывает ожидание ответа и черновик рассылки).
3. **Команда во время мастера обратной связи** становилась текстом обращения; теперь
   неизвестная команда отменяет черновик. Текст длиннее 4000 символов вызывал
   необработанное исключение без ответа — теперь пользователь видит понятную подсказку
   (новый ключ `feedback.text_invalid`).
4. **Тяжёлые картинки меню.** PNG 2,3 МБ загружались в Telegram при каждом переходе.
   Ассеты пережаты в JPEG 1280 px (4,6 МБ → 0,42 МБ), `ScreenRenderer` кэширует
   Telegram `file_id` загруженного файла (символические ссылки категорий — одна загрузка).
5. **Карточка актуального события без кнопки.** У событий со стримом источник закрывает
   регистрацию заранее (реальный пример — событие 23.10.2026). Если ссылки регистрации
   нет, показывается «Подробнее» со ссылкой трансляции.
6. **Двойной middleware.** Пользователь резолвился (upsert в БД) дважды на каждое
   обновление — в admin- и user-роутере. Middleware зарегистрирован один раз на корневом
   роутере.
7. **Вечный `quota_request_too_large`.** Резерв оценивается по байтам UTF-8 (для
   кириллицы в 4–6 раз больше реального расхода: ~4000 против ~600 токенов). Событие с
   длинным описанием никогда бы не классифицировалось. Резерв в адаптере ограничен
   ёмкостью квоты `min(GROQ_TPM, GROQ_TPD)`; фактический usage по-прежнему заменяет резерв.
8. **Переклассификация при сбое Groq** немедленно переносила событие с корректными
   категориями в «Другое» на время повторов (до 24 ч), а затем закрепляла `other`.
   Теперь сохраняются прежние категории; «Другое» по-прежнему используется для новых
   событий без классификации.
9. **Отозванный доступ.** Пользователь, удалённый из `ALLOWED_TELEGRAM_IDS`, получал
   уведомления и рассылки, пока сам не напишет боту. При старте `reconcile_access`
   приводит `access_granted` в соответствие с конфигурацией (в обе стороны).
10. **Очередь классификации.** Первичный импорт содержит ~206 архивных и ~2 актуальных
    события; очередь шла по `event_id`. Предстоящие события теперь классифицируются первыми.
11. **Дайджест без ссылок.** В записи нового события/изменения добавлена безопасная ссылка
    регистрации (или трансляции); превью ссылок отключено. Для отмен ссылка не выводится.
12. **Зависимости.** `pip-audit` нашёл 10 известных уязвимостей (aiohttp 3.14.3 ×8,
    multidict 6.8.0, certifi 2026.7.22). Обновлены только эти пакеты: aiohttp 3.14.5,
    multidict 7.1.0, certifi 2026.10.19; повторный аудит — 0.

## Проверено без замечаний

- Callback data не содержит пользовательского ввода; карточка события открывается только
  из текущей страницы каталога; admin-действия проверяют `ADMIN_TELEGRAM_IDS`, черновик
  рассылки — автора.
- HTML-экранирование экранов, plain-text для admin/feedback/дайджестов, строгая
  нормализация URL (без userinfo, приватных IP, не-HTTP схем).
- Общие поля RU/KZ в живом API совпадают для всех 208 событий (ложных alert нет).
- Секреты редактируются в логах; Docker non-root/read-only.

## Оставлено как известные ограничения

- KZ-строки интерфейса заполнены по запросу пользователя (111 ключей, `ensure_public_kz_ready`
  проходит). Перевод выполнен агентом; перед публичным запуском желательна вычитка носителем.
- Пропускная способность рассылок: 20 сообщений за 30 с (≈1000 получателей за 25 мин) —
  безопасно для лимитов Telegram, при росте аудитории можно ускорить.
- Alert `gpt_prolonged_failure` агрегирует все исторические fallback без срока давности.
