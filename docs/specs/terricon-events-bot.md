# Спецификация Terricon Events Bot v1

## 1. Назначение и границы

Terricon Events Bot — независимый неофициальный Telegram-бот для просмотра мероприятий Terricon Valley, подписки на тематические категории и получения уведомлений.

В первую версию входят:

- каталог актуальных и прошедших мероприятий;
- RU/KZ-интерфейс;
- GPT-классификация по фиксированным категориям;
- фильтры по категории, периоду, формату и языку мероприятия;
- ссылки на регистрацию или материалы события;
- подписки на категории либо на все мероприятия;
- уведомления о новых событиях и важных изменениях;
- обратная связь с двусторонними ответами через бота;
- базовые admin-команды и служебные рассылки;
- закрытая beta с последующим публичным запуском.

Не входят в v1: текстовый поиск, избранное, персональные напоминания и экспорт в календарь.

## 2. Пользовательский интерфейс

### Навигация

Бот использует один редактируемый inline-экран, чтобы не засорять чат. Главное меню:

- «Мероприятия»;
- «Подписки»;
- «Настройки»;
- «Обратная связь»;
- «О проекте».

Первый запуск:

1. Выбор RU или KZ.
2. Краткий текст о неофициальном статусе, источнике данных и приватности.
3. Кнопка «Продолжить».

### Каталог

Путь: «Мероприятия» → «Актуальные / Архив» → «Все мероприятия / категория».

Категории:

1. `development_it` — Разработка и IT;
2. `ai_data` — AI и Data;
3. `business_finance` — Бизнес и финансы;
4. `marketing_sales` — Маркетинг и продажи;
5. `design_creative` — Дизайн и креатив;
6. `startups_products` — Стартапы и продукты;
7. `career_education_hr` — Карьера, образование и HR;
8. `soft_skills_languages` — Soft skills и языки;
9. `other` — Другое.

Фильтры применяются совместно:

- актуальные: сегодня, 7 дней, 30 дней, все;
- архив: 30 дней, 3 месяца, весь архив;
- формат: онлайн, офлайн, гибрид;
- язык мероприятия: русский, қазақша, English;
- одна категория либо все.

Сортировка: актуальные по возрастанию даты, архив по убыванию. Событие считается актуальным до конца дня проведения по `Asia/Almaty`.

Результаты показываются страницами по 5 кратких пунктов. Размер задаётся `EVENTS_PAGE_SIZE`. Нажатие на событие открывает карточку с постером, названием, датой, форматом, адресом, языком, категориями и кнопками:

- «Описание»;
- «Регистрация» для актуальных;
- «Запись» или «Подробнее» для архива;
- «Назад / Вперёд / К списку».

Разрешены только корректные HTTP(S)-ссылки. При недоступном постере используется текстовая карточка.

### Изображения и локализация

В настройках есть независимые переключатели:

- показывать оформление меню;
- показывать постеры мероприятий.

Декоративные файлы хранятся в репозитории:

- `assets/common/main.*`;
- `assets/common/categories/<category_slug>.*`;
- необязательные переопределения в `assets/ru/` и `assets/kz/`.

Порядок fallback: локализованная картинка → общая → экран без картинки. Отсутствие картинки не блокирует запуск.

RU-строки поставляются полностью. Для KZ создаётся полный locale-файл с теми же ключами и явными TODO; отсутствующие строки временно используют RU fallback. Перед публичным включением KZ все строки должны быть заполнены и проверены пользователем.

### «О проекте»

RU-текст фиксирует:

> Terricon Events Bot — независимый неофициальный проект и не связан с командой Terricon Valley. Данные о мероприятиях получены из публично доступного API Terricon Valley и могут изменяться. Регистрация проходит по внешней ссылке организатора. Сообщить об ошибке или оставить предложение можно через раздел «Обратная связь». Автор проекта не публикует личные данные.

Добавляется кнопка официального сайта. Личный аккаунт автора нигде не показывается.

## 3. Получение и обработка событий

Каждые 6 часов выполняются шесть запросов:

- `lang=ru|kz`;
- `theme=it|business|marketing`.

Endpoint без `theme` не используется. Запросы тем можно выполнять параллельно с ограниченной конкуренцией.

Для каждого endpoint:

- таймаут;
- первоначальный запрос и до трёх повторов;
- экспоненциальная задержка с jitter;
- поддержка `Retry-After`;
- после исчерпания попыток — ожидание следующего шестичасового цикла.

События объединяются по числовому `id`. Локализации хранятся отдельно. Если один язык временно недоступен, сохраняется последняя успешная версия.

Первичная загрузка считается baseline: данные сохраняются и классифицируются, но уведомления не отправляются.

Исчезнувшее событие скрывается только после двух последовательных успешных циклов, в которых оно отсутствует в обеих локализациях своей темы. Частичный сбой endpoint не увеличивает счётчик отсутствия.

При сбое синхронизации:

- каталог продолжает работать из PostgreSQL;
- пользователь видит предупреждение об устаревших данных;
- администратор получает одно дедуплицированное уведомление;
- сохранённые события не удаляются.

## 4. GPT-классификация и переводы событий

Используется модель `gpt-5.6-luna` через Responses API и официальный Python SDK. Модель поддерживает структурированный вывод; текущая официальная цена составляет $0.20 за миллион входных и $1.20 за миллион выходных токенов. [OpenAI Docs](https://developers.openai.com/api/docs/models/gpt-5.6-luna)

Контракт классификатора:

```text
categories: 1–3 значения из CategorySlug
```

Правила:

- `other` не совмещается с другими категориями;
- результат валидируется как закрытый enum;
- сохраняются модель, версия prompt, время и semantic hash события;
- повторная классификация выполняется только для нового события, при изменении названия/описания/аудитории/спикера или вручную администратором;
- изменения даты, ссылки или постера не вызывают переклассификацию.

Если GPT недоступен, событие сразу показывается в «Другое», но уведомление откладывается. Классификация повторяется до 24 часов; после этого `other` закрепляется и событие рассылается подписчикам «Другое» и «Все».

GPT-перевод разрешён только когда API не дал официальную RU- или KZ-локализацию события. Такой текст помечается как машинный и заменяется официальной версией при её появлении. Интерфейс и служебные рассылки GPT не переводит.

`OPENAI_MONTHLY_BUDGET_USD=5` задаёт мягкий месячный лимит по usage API и настраиваемым тарифам. После исчерпания лимита новые GPT-вызовы приостанавливаются, администратор получает alert, а события проходят стандартный fallback в `other`.

## 5. Подписки и уведомления

Пользователь выбирает:

- несколько отдельных категорий; либо
- взаимоисключающую подписку «Все новые мероприятия».

Одно событие с несколькими совпавшими категориями включается в дайджест один раз.

После каждого успешного цикла формируется один логический дайджест с секциями:

- новые мероприятия;
- важные изменения.

Важные изменения:

- дата или время;
- формат;
- адрес;
- регистрационная ссылка;
- название;
- отмена/исчезновение события.

Для изменения категорий получатели определяются по объединению старых и новых категорий. Доставка идемпотентна: перезапуск приложения не создаёт повторных уведомлений.

Тихие часы: 22:00–09:00 `Asia/Almaty`. Синхронизация продолжается, но сообщения копятся и объединяются после 09:00. При превышении лимита Telegram дайджест технически разбивается на несколько сообщений.

## 6. Feedback, приватность и администрирование

### Обратная связь

Сценарий:

1. «Ошибка / Идея / Другое».
2. Текст обращения.
3. Необязательное одно фото.
4. Предпросмотр сведений, передаваемых админу.
5. Подтверждение.

Админу показываются имя и `@username`. Ограничение — не более трёх новых обращений за 24 часа. Фото не скачивается: хранится Telegram `file_id`.

Тикет поддерживает двусторонний диалог и закрытие. Ответ администратора копируется ботом, а не пересылается, поэтому аккаунт администратора не раскрывается. Закрытые обращения удаляются через 90 дней.

Пользователь может удалить профиль, настройки, подписки, тикеты и связь с Telegram `file_id`. Перед удалением показывается предупреждение, что уже доставленные сообщения в admin-чате Telegram могут сохраниться.

### Admin-функции

Доступ определяется `ADMIN_TELEGRAM_IDS`. Предусмотреть:

- состояние приложения и endpoint;
- статистику пользователей, подписок, событий и GPT-расхода;
- ручную синхронизацию;
- повторную классификацию события;
- просмотр, ответ и закрытие тикетов;
- блокировку и разблокировку отправителя;
- служебную рассылку.

Рассылка поддерживает текст и одно фото. Админ выбирает RU, KZ или обе аудитории; для обеих локалей вводятся два текста вручную. Обязательны предпросмотр и отдельное подтверждение. Прогресс и результаты сохраняются в БД, чтобы рассылку можно было продолжить после перезапуска.

## 7. Архитектура и хранение

Стек:

- Python 3.13;
- aiogram 3, long polling;
- PostgreSQL;
- SQLAlchemy 2 async + asyncpg;
- Alembic;
- httpx;
- OpenAI Python SDK;
- APScheduler;
- pydantic-settings;
- uv;
- pytest, Ruff, mypy;
- Docker Compose.

Один контейнер приложения обслуживает Telegram, синхронизацию, outbox и административные задачи. Redis и отдельный worker в v1 не используются. Пересекающиеся ручные и плановые синхронизации защищаются блокировкой.

Основные сущности БД:

- users и настройки;
- subscriptions;
- events;
- event_localizations;
- event_categories;
- classification metadata;
- sync_runs и состояние endpoint;
- notification_outbox/deliveries;
- feedback_tickets/messages;
- broadcasts/deliveries;
- beta allowlist и заблокированные пользователи.

Декоративные картинки входят в Docker-образ. Постеры событий передаются Telegram по URL и локально не кэшируются.

Многошаговые пользовательские и admin-сценарии сохраняют состояние в PostgreSQL, чтобы перезапуск не терял подтверждённые операции.

## 8. Конфигурация и развёртывание

В `.env.example` документируются как минимум:

```text
BASE_URL
TELEGRAM_BOT_TOKEN
OPENAI_API_KEY
OPENAI_MODEL=gpt-5.6-luna
OPENAI_MONTHLY_BUDGET_USD=5
DATABASE_URL
ADMIN_TELEGRAM_IDS
ACCESS_MODE=allowlist|public
ALLOWED_TELEGRAM_IDS
APP_TIMEZONE=Asia/Almaty
SYNC_INTERVAL_HOURS=6
SYNC_MAX_RETRIES=3
EVENTS_PAGE_SIZE=5
QUIET_HOURS_START=22:00
QUIET_HOURS_END=09:00
FEEDBACK_RETENTION_DAYS=90
LOG_LEVEL
```

Секреты не попадают в Git и логи. Telegram ID, тексты обращений и токены не записываются в структурированные логи.

Развёртывание:

- приложение и PostgreSQL в одном Docker Compose на VPS;
- отдельный persistent volume БД;
- ручное обновление через SSH и Docker Compose;
- миграции перед запуском новой версии;
- healthcheck, graceful shutdown и автоматический restart;
- ежедневный `pg_dump` вне volume БД;
- хранение семи копий;
- документированная проверка восстановления.

Beta запускается с `ACCESS_MODE=allowlist`. Публичный режим включается конфигурацией без изменения кода.

## 9. Наблюдение и обработка ошибок

- Структурированные stdout/stderr-логи.
- Admin-alerts при длительном сбое API, GPT, PostgreSQL, outbox или рассылки.
- Одинаковые ошибки группируются, чтобы не спамить администратора.
- Невалидная запись API пропускается и логируется, но не ломает весь цикл.
- При расхождении общих полей RU/KZ применяется детерминированный приоритет RU с предупреждением админу.
- Ошибка отправки одному пользователю не останавливает дайджест другим.
- После Telegram `403` пользователь помечается неактивным, его подписки больше не обрабатываются.
- Значения callback-кнопок используют короткие стабильные идентификаторы и не содержат пользовательский ввод.

## 10. Проверка и критерии приёмки

Тесты должны покрывать:

- разбор всех трёх тем и объединение RU/KZ по ID;
- дедупликацию, semantic hash и важные изменения;
- частичные сбои, повторы и работу из кэша;
- два цикла отсутствия перед скрытием;
- первоначальную загрузку без рассылки;
- строгую GPT-схему, `other` и 24-часовой fallback;
- временный перевод отсутствующей локали и замену официальным;
- фильтры, сортировку и страницы по 5 элементов;
- обе настройки изображений и fallback файлов;
- подписку «Все» и мультиметочные категории без дублей;
- тихие часы и идемпотентный outbox;
- feedback, лимиты, ответы, блокировку и удаление данных;
- предпросмотр, подтверждение и возобновление admin-рассылки;
- миграции PostgreSQL и запуск чистого Docker Compose.

Автоматические тесты используют фикстуры и mock-сервисы: реальные сообщения и платные OpenAI-запросы не выполняются. Отдельная ручная smoke-команда проверяет публичный Terricon API.

Готовность закрытой beta: все основные сценарии работают на RU, KZ использует подготовленный шаблон с fallback, синхронизация и восстановление после сбоев проверены. Готовность публичного запуска: KZ-строки проверены пользователем, создан свежий backup, пройдены smoke-тесты и выключен allowlist.

## 11. Документация

После утверждения эта спецификация переносится в `docs/specs/terricon-events-bot.md`. Перед реализацией создаётся подробный план в `docs/plans/`, привязанный к спецификации; после выполнения он помечается завершённым.

Текущее исходное состояние: проект не содержит кода и Git-репозитория, присутствует только `.env` с `BASE_URL`.
